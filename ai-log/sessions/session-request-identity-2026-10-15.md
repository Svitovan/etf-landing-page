# Исправление идентичности заявки — Codex, 2026-10-15

## Запрос пользователя

«помоги с реализацией 1 пункта» — конфликт повторного requestId с изменёнными данными из последней проверки готовности.

## Выполнено

- Добавлены каноническое сравнение заявки, типизированная ошибка и HTTP 409 без исходных данных.
- Сохранён ID одинакового повтора; явная отправка изменённых данных получает новый ID. После конфликта автоматической повторной отправки нет.
- Через Supabase CLI создана новая миграция `20261015101054_enforce_lead_request_identity.sql`; старый SQL-файл не изменён. Функция сравнивает email, ETF, сумму, privacy и dataset; использует транзакционную блокировку request ID и прежние закрытые права.
- Обновлены T18 и документация; добавлены тесты клиентской идентичности, RPC-ошибок и SQL-целостности.
- Изучены документация Supabase Database Functions, PostgREST custom errors и PostgreSQL advisory locks; применены локальные Supabase skills.

## Фактическая проверка

52/52 Vitest, lint, typecheck и production build прошли. Новая функция и SQL-тест проверены на настоящем Supabase Postgres в общей транзакции с откатом. Пройдены совпавший повтор, нормализация старого массива ETF, пять конфликтов, неизменность исходной записи и права. После отката каталог подтвердил отсутствие новой проверки в production-функции. Параллельная нагрузка и браузерный 409 не проверялись.

При первом объединении SQL в JavaScript строковая замена интерпретировала `$$` как специальный шаблон замены, и сервер отклонил запрос с синтаксической ошибкой. Использована функция обратного вызова для буквальной вставки SQL; повторная проверка прошла. Это ошибка сборки проверочного запроса, а не файла миграции.

Commit/push, постоянная миграция, деплой и отправка сообщений не выполнялись. Шаги включения: `docs/qa-idempotency-2026-10-15.md`. Остальные findings предыдущего аудита остаются вне этой реализации.
