# Проверка исправления идентичности заявки — 2026-10-15

## Что исправлено

Пункт 1 из `readiness-verification-4465301.ru.md`: повторный `requestId` с изменённым содержимым больше не должен возвращать успешный результат старой заявки.

Одинаковая заявка возвращает исходный результат без новой записи. Изменённая заявка получает HTTP 409 с `errorCode: IDEMPOTENCY_CONFLICT`, без исходного email или ссылки на чужие параметры. Сравниваются нормализованный email, множество ETF, сумма, версия privacy и версия dataset. Регистр/окружающие пробелы email и порядок/дубликаты ETF не меняют идентичность. Analytics session исключена из сравнения и не переписывается при повторе.

Форма сохраняет ID при повторе после сетевой ошибки. Если пользователь меняет данные и снова отправляет форму, создаётся новый ID. После 409 новый ID создаётся только при следующем явном нажатии отправки. Отпечаток данных существует только в памяти компонента, не записывается в URL, хранилище браузера или аналитику.

Новых постоянных тестовых контактов эта проверка не оставила. Тест не моделировал несколько параллельных соединений; проверены наличие и время жизни блокировки, а не нагрузочная устойчивость.

API-тест вызывает настоящий Route Handler с локальным хранилищем, проверяет 409, отсутствие утечки исходных данных и успешный повтор исходной заявки. RPC-тесты отдельно проверяют преобразование PostgREST `PT409` в типизированный конфликт. Браузерный сценарий 409 и live HTTP 409 после постоянного деплоя пока не проверены.

4. Проверить через опубликованный `/api/leads`: первая валидная заявка → 200, тот же ID и данные → 200 с `isDuplicateRequest: true`, тот же ID и изменённая сумма → 409 с `IDEMPOTENCY_CONFLICT`. Убедиться, что осталась одна submission с исходными данными. Использовать отдельную тестовую среду или исключить записанный тестовый request ID из бизнес-отчёта.
