# Тестовый трафик отдельно от конверсий

Реализовано 15 октября 2026. `npm run report:funnel` по умолчанию считает только трафик, не помеченный тестовым. Сами записи сохраняются в базе.

## Как устроено исключение

- `lead_submissions.is_test` и `analytics_sessions.is_test` — серверные boolean-поля. Публичный lead/event API не принимает от пользователя управление ими.
- Перед сохранением submission Postgres распознаёт email на точных зарезервированных доменах `example.com`, `example.net`, `example.org`, `test`, `invalid`, а также поддоменах `.test`/`.invalid`. Он отмечает заявку и связанную session. Префикс `qa` в обычной почте не является основанием для автоматической маркировки.
- Существующие тестовые заявки автоматически размечены по этим доменам. Сессии связываются также через `form_submit_attempted.properties.requestId`: исключается исторический распад одной проверки на несколько session. Позднее событие тоже помечает свою session. Новой заявке в заранее помеченной session наследуется test-флаг.
- Вся тестовая session исключается **из числителя и знаменателя CVR**, всех шагов воронки и UTM-разбивки. При смешанном использовании session подход консервативный: вся она считается загрязнённой тестом. Даже заявка со старым `is_test=false` в такой session не попадает в статистику.
- Заявка без аналитической session также исключается, если помечена тестовой. Контакты считаются как distinct lead IDs оставшихся заявок: тест одного контакта не исключает его отдельную настоящую конверсию в другой session.
- Шаги calculator/form/report считаются внутри наблюдаемых нетестовых session с `landing_observed`. Согласие и правила приватности не менялись; служебный отчёт не читает email/IP и выводит только агрегаты.
- Отчёт показывает отдельно число исключённых тестовых session/отправок. Если наблюдаемых нетестовых session нет, CVR — **N/A**, а не 100% демонстрационного сценария или измеренный рекламный 0%. UTM сама по себе не доказывает оплаченный рекламный переход.
- REST-чтение имеет стабильную пагинацию по id по 1000 строк, без прежнего молчаливого ограничения первой страницей. Чтение трёх таблиц не является одной snapshot-транзакцией: при активном потоке событий отчёт следует строить после закрытия окна конверсии/повторять после стабилизации данных.

## Существующий демонстрационный набор

Пользователь прямо подтвердил в этом чате: **«Нет, все посещения были тестовыми»**. На этом основании, отдельно от общей миграции, в одной транзакции помечен весь существовавший набор с `created_at <= 2026-10-15 14:14:57.874269 UTC`:

| Набор на момент подтверждения | Сохранено | Помечено тестовым |
|---|---:|---:|
| Заявки | 9 | 9 |
| Аналитические session | 23 | 23 |

Не выполнялись DELETE, сброс базы или автоматическое исключение будущего трафика по этому cutoff. Без подтверждения пользователя неизвестные старые session не объявлялись тестовыми. Изначально 7 заявок распознаны по reserved domains, ещё 2 найдены в демонстрационной session из скриншотов; затем подтверждение позволило исключить и остальные session без заявок. В миграции нет личных адресов, сгенерированных ID или команды «всё объявить тестом».

После этого выполнен **один реальный production HTTP сценарий** с синтетической заявкой: создание consent session ad_b → landing/event → сохранение example.com → GET report 200 → report_opened. DB read-only проверка подтвердила `is_test=true` у заявки и session. Числитель/знаменатель/UTM не изменились; исключённые счётчики выросли на 1:

- **10 тестовых заявок, 24 тестовые session**, записей не удаляли.
- Нетестовые наблюдаемые session: **0**, заявки: **0**, контакты: **0**, CVR: **N/A**.
- [Агрегированный протокол до/после](../output/analytics/test-traffic-verification-2026-10-15.json). Это техническая проверка, не результат рекламы. Счётчики относятся к текущему хранимому набору и со временем меняются при штатной ретенции.

## Будущие проверки

Самый простой путь — использовать `demo@example.com`: сервер автоматически исключит такую заявку и её session. Для проверки с обычной почтой **до прохождения пути** пометьте QA-session серверной командой. ID виден в ответе `/api/analytics-session` в Network; не публикуйте его как рекламную метку.

```sh
# Только preview, ничего не меняет
npm run analytics:mark-test -- --session-id=SESSION_ID

# Пометить известную QA-session и её заявки
npm run analytics:mark-test -- --session-id=SESSION_ID --apply

# Или исправить классификацию уже известной демонстрационной заявки
npm run analytics:mark-test -- --request-id=REQUEST_ID --apply

# Отчёт без тестов
npm run report:funnel
```

Команда требует локальной серверной `.env` с service key, принимает ровно одну цель, по умолчанию preview. `mark_test_traffic` выполняет изменения атомарно, разрешена только service_role; anon/authenticated не имеют EXECUTE. При неизвестной цели/ошибке БД/невалидном результате — exit 1 без приватных деталей. Она ничего не удаляет и не предлагает массово помечать обычный трафик. При ошибочной пометке обычной session администратор может в транзакции снять флаг сначала с session, затем с её заявок; reserved-domain заявки остаются тестовыми по правилу сервера.

Новые session не имеют test-флага по умолчанию. Старую QA-session не нужно использовать для проверки реальной рекламной конверсии: создайте новую сессию после сброса согласия/истечения cookie. При новой проверке обычной почтой снова потребуется предварительная служебная пометка.
