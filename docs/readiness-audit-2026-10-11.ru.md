## Вывод

Проект — работающий прототип с существенной частью frontend, контента и документации. Это пока не завершённый P0 и не готовая к рекламе landing page. Заявление handoff «E0–E8 завершены, осталось только развернуть» не соответствует коду и воспроизведённым результатам.

## Приоритетные дефекты и действия

### A01 — P0: ложный успех при отсутствии постоянного хранилища

Файлы: `src/lib/server/db.ts:59`, `src/lib/server/lead-service.ts:106`, `src/app/api/leads/route.ts:80`.

В production сборке без Supabase отправлен синтетический `audit@example.com`: HTTP 200, `success:true`, выдан report URL. Код безусловно использует `memoryStore`, в том числе при `NODE_ENV=production`. После перезапуска память исчезнет; разные процессы/функции могут иметь разные store. CLI funnel запускается отдельным процессом и не видит память веб-сервера.

Исправление: разрешить память только явным тестовым режимом; в production при отсутствии конфигурации возвращать 503. Подключить постоянную БД, проверить наличие lead/submission и сохранность после перезапуска. Это нарушение E4/R04 и §10/16 плана.

### A02 — P0: запись lead и submission не атомарна

Файл: `src/lib/server/lead-service.ts:31–100`; SQL-миграция содержит таблицы, но не транзакционную RPC.

Сначала выполняется поиск, затем отдельный insert контакта, затем отдельный insert заявки. Если второй insert откажет, контакт останется без заявки. Параллельные запросы могут оба не найти контакт/requestId, столкнуться с UNIQUE и вернуть ошибку одному клиенту. Наличие уникальных ограничений полезно, но не делает несколько HTTP-запросов транзакцией.

Исправление: единая транзакционная операция с обработкой конфликтов и идемпотентности; проверка конкурентных запросов и rollback на реальной тестовой БД. Структурный дефект подтверждён кодом; отказ реального Supabase в этом аудите не имитировался.

### A03 — P1: идемпотентность не соответствует retry-сценарию

Файлы: `src/components/LeadForm.tsx:43`, `src/lib/server/lead-service.ts:37,108`.

Форма создаёт новый requestId при каждом submit. Если сервер сохранил заявку, но ответ потерялся, повтор создаст новую submission. При этом тот же requestId с изменёнными email/суммой принимается как успех: HTTP-проверка вернула 200 и новый report URL для 250000 вместо 100000, `isDuplicateRequest:true`.

Исправление: хранить ID одной попытки на клиенте до определённого результата; на сервере сравнивать каноническое содержимое или hash, отклонять конфликт и возвращать результат оригинальной заявки. Добавить timeout/retry и changed-payload тесты.

### A04 — P1: мобильное горизонтальное переполнение

Файлы: `src/components/Header.tsx`, `src/components/CostCalculator.tsx:199`.

Локальная production landing: при ширине 320 px и 390 px ширина документа 413 px. На 320 px навигация выходит до x≈333; карточка SPY в жёсткой трёхколоночной сетке калькулятора — до x≈413. Горизонтальный scrollbar виден на скриншоте. Первичный экран с cookie-панелью также скрывает значительную часть полезного содержимого.

Исправление: адаптивная шапка, одноколоночный/переносимый вывод расчёта на узком экране, корректные минимальные размеры grid children. Не маскировать проблему `overflow-x:hidden`. Повторить 320/360/390 и desktop, увеличенные значения суммы и клавиатуру.

### A05 — P1: неполная воронка и истечение сессии

Файлы: `src/lib/analytics-client.ts:37–96`, `src/components/ConsentBanner.tsx:28`, `src/components/LandingPageClient.tsx:29`, `scripts/funnel-report.ts:39,95`.

- `comparison_viewed`, `lead_cta_clicked`, `report_opened` перечислены в типах/schema, но вызовов этих событий в UI нет. Открытие материала невозможно подтвердить штатным событием.
- Новая сессия создаётся только при нажатии Accept. Когда 30-минутная cookie истекла, localStorage всё ещё хранит granted: баннер не показывается, события получают 403, повторной инициализации нет.
- Знаменатель funnel — все `analytics_sessions`, а не сессии с `landing_observed`. Например, созданная сессия с потерянным landing-event уже попадёт в CVR.
- Запросы funnel не проверяют ошибки и не имеют пагинации/временного интервала; сбой может выглядеть как нулевой отчёт, большие наборы могут считаться неполно.
- При отсутствии Supabase `npm run report:funnel` выводит нули из своей пустой памяти — это не доказательство рабочего пути пользователя.

Исправление: подключить реальные события, восстановление сессии, определить единичность шагов, считать distinct landing sessions и сохранённые submissions согласованно. Приложить обезличенную цепочку из постоянного хранилища. Не добавлять отдельное клиентское `lead_saved`: источник конверсии submissions выбран правильно.

### A06 — P1: недостаточные ограничения аналитики и проверки согласия

Файлы: `src/lib/validation.ts:40`, `src/app/api/leads/route.ts:77`, `src/app/api/analytics-session/route.ts`, `src/lib/server/analytics.ts:22`.

HTTP POST `/api/events` с `properties.email` и `properties.rawUrl` принят с 200. Schema разрешает произвольные строковые ключи/значения; сервер не гарантирует отсутствие PII, хотя штатный UI сейчас не отправляет email.

Lead endpoint прикрепляет cookie без `isSessionValid`, включая устаревшую/отозванную/поддельную. Сессионная cookie — случайный ID без подписи; `ANALYTICS_SESSION_SECRET` не используется. Случайный UUID сам по себе не доказывает практическую возможность угадать чужую сессию, но требование плана о подписи не реализовано. Ошибки insert/update сессии Supabase не проверяются.

Исправление: отдельная строгая schema свойств каждого события, лимиты строк/тела, серверная проверка срока и активности сессии при сохранении заявки, обработка ошибок создания/отзыва. Подпись либо явно обоснованный безопасный пересмотр решения.

### A07 — P1: защита API и rate limit не завершены

Файлы: `src/app/api/leads/route.ts:6`, `src/lib/server/rate-limit.ts:20–54`.

Запрос с посторонним Origin принят (200); `APP_ORIGIN` не используется. Content-Type не проверяется. Ограничение уже прочитанного тела использует число JS-символов вместо байтов. Указанный в плане порядок проверок не выполнен.

В Supabase rate limit выполняется read → update, а не атомарное увеличение. Параллельные запросы способны терять increments. Ошибки Supabase возвращаются объектом `error`, который здесь игнорируется: успешный ответ лимитера не подтверждает успешную запись bucket. Есть постоянная fallback-соль; доверенность IP-заголовков хостинга не документирована.

Исправление: Origin/Content-Type/byte-size проверки; атомарный лимитер, явное поведение при отказе и обязательная production-конфигурация. Атака на реальную БД не проводилась. Отличие 10 попыток вместо рекомендуемых 5 само по себе не блокер — важна надёжность.

### A08 — P1: QA-доказательства и статусы завышены

Файлы: `tests/backend.test.ts`, `docs/qa-report.md`, `docs/launch-checklist.md`, `docs/handoff.md`.

- T07 вызывает service с повреждённым payload, но не моделирует storage failure и не требует, чтобы исключение вообще произошло. Тест способен пройти без assertions.
- T14 сравнивает строку с `lead_saved`, не вызывает endpoint. В этом аудите реальный endpoint отдельно проверен: действительно возвращает 400.
- T15 ищет `ENABLE ROW LEVEL SECURITY` в SQL, не проверяет доступ anon к реальной БД.
- T10 проверяет несуществующий session ID в сервисе, не browser requests до/после отказа.
- T16 проверяет memory limiter, не HTTP 413 и не конкурентность БД.
- Нет E2E-набора/конфигурации Playwright, браузерных скриншотов, Lighthouse-отчёта или подтверждения печати.
- Checklist считает R15 выполненным на основании готовности конфигурации, а handoff предлагает создать remote, который уже существует.

Исправление: снять необоснованные статусы, добавить минимальные интеграционные и browser проверки вокруг перечисленных рисков. Сохранять реальные результаты, а не отмечать покрытие по названиям тестов.

### A09 — P1: не все финансовые утверждения имеют доказательства

Файлы: `src/components/CzechContext.tsx:64,80`, `src/components/SourcesFaq.tsx`, `src/components/Hero.tsx`, `data/etfs.json`.

В UI есть диапазон комиссии обмена «часто 0.5–1.5%», налоговые 15%, формулировки о крупнейших/наиболее ликвидных фондах. Эти числа/сравнения не прослеживаются до первичных источников в dataset. Это подтверждённая проблема доказательств, а не заявление, что каждое число неверно. Юридическую/налоговую корректность всех формулировок этот аудит не удостоверяет.

Ставки в Hero и части report захардкожены отдельно от dataset. Изменение JSON не обновит все обещания. Общая обзорная страница NYSE не доказывает листинг конкретного ticker, хотя проверенные страницы эмитентов подтверждают его. `validate-data.ts` проверяет URL лишь по префиксу `http`, не открывает источник, не сверяет `displayPercent` с rate и не покрывает все metadata-поля. Сообщение скрипта «full primary evidence» сильнее фактической проверки.

Исправление: единый источник чисел, точные доказательства у каждого публикуемого финансового факта, осторожные тексты вне подтверждённого набора. Не выдавать даты отчётности иных показателей за asOf expense ratio.

### A10 — P1: отчёт и выбор не полностью соответствуют обещанию

Файлы: `src/components/LeadMagnet.tsx:99`, `src/components/LandingPageClient.tsx:27`, `src/app/report/page.tsx:29`.

В LeadMagnet обещаны определения NAV, Bid-Ask spread и реинвестирования дивидендов. В report словарь содержит Expense Ratio, KID, UCITS; NAV лишь упомянут, остальные обещанные определения отсутствуют. Вместо кликабельных первичных источников внизу общий текст с названиями организаций.

Отдельный выбор карточки ETF локален компоненту сравнения; форма всегда получает `[VOO, IVV, SPY]`. Report игнорирует `etfs` даже при прямом URL `etfs=VOO`. Если кнопки задуманы только как фильтр просмотра, это нужно ясно обозначить и согласовать с планом; иначе поднять состояние и сохранять выбор. Форма обещает немедленное открытие report, фактически показывает ещё одну кнопку — небольшой copy/UX-разрыв.

Исправление: согласовать обещание с содержанием, добавить источники/дату/полный словарь, сохранить параметры и визуально проверить print/PDF.

### A11 — P1: privacy и удаление данных не готовы к публичному сбору

Файлы: `src/app/privacy/page.tsx`, `scripts/cleanup-data.ts:68–79`, SQL-миграция.

Privacy не называет фактического оператора и конкретный контакт; ссылка «обратиться в репозиторий» не заменяет контакт для непубличного обращения. Обещано удаление максимум за 30 дней, но расписания выполнения cleanup в проекте нет.

Cleanup обращается к `rate_limit_buckets.id` и `created_at`, которых нет в миграции (есть `bucket_key`, `request_count`, `expires_at`). Supabase-ветка очистки bucket не соответствует собственной схеме; ошибки не проверяются. Memory-тест этого не замечает. Скрипт также печатает targetEmail в stdout при адресном удалении.

Исправление: реальные сведения оператора/контакта, точное описание провайдеров и сроков, очистка по существующей колонке, проверка ошибок и проверяемый процесс удаления. Это сравнение с требованиями проекта, не юридическое заключение.

## Дополнительные замечания

- Рекламные HTML-макеты — допустимый демонстрационный формат; экспорт PNG полезен, но не заменяет исправление critical path.
- Privacy banner называет аналитику «анонимной», тогда как связанная с lead session псевдонимна. Тексты следует согласовать с моделью данных.
- Honeypot присутствует в accessibility tree браузера: opacity/нулевой размер и tabIndex не скрывают его от screen reader. Нужно корректное скрытие от assistive technology.
- Report называет UCITS доступными у всех европейских брокеров — чрезмерно универсальное утверждение, требующее исправления/доказательства.
- Гипотезы A/B не требуют реального запуска к сдаче. Но нельзя утверждать достаточность 1000 сессий для alpha=0.05/power=0.80 без baseline и MDE. Прогноз 3–7% допустим как предположение; consent rate не является прямым доказательством его численного диапазона.
- README использует `file:///c:/...` для внутренних документов: такие ссылки неудобны проверяющему на GitHub. Нужны относительные ссылки.
- `ai-log/sessions/session-e0-e8.md` полезен как конспект. Требуется доступный исходный экспорт инструмента либо честное объяснение отсутствия; нельзя задним числом сочинять диалог. Подлинность перечисленных прежних ошибок по одному конспекту установить нельзя.

## Порядок завершения

1. **Вернуть достоверность backend:** убрать production memory-success, реализовать транзакцию, корректный retry и устойчивый лимит; подключить БД. Критерий: одна сохранённая заявка после timeout/retry, ошибка БД не даёт успех.
2. **Закрыть мобильный путь и содержание:** исправить overflow, проверить калькулятор → форма → материал без аналитики, синхронизировать выбор/словарь/источники, проверить печать.
3. **Довести измерение:** allowlist свойств, проверка и обновление сессий, все реальные события, корректный знаменатель; сохранить обезличенное доказательство из БД.
4. **Закрыть достоверность и privacy:** источники дополнительных чисел, metadata, оператор/контакт, работающая очистка без утечки данных в логи.
5. **Перепроверить и обновить документы:** интеграционные проверки T05–T16, browser smoke на 320/360/390, Lighthouse mobile, действительный AI-export, честная QA-матрица.
6. **Завершить E9:** публичный HTTPS deploy, оба UTM URL, запись тестовой заявки в production и report, соответствие commit, заполненные ссылки письма. Отправка письма — только по отдельному поручению.

Точная оценка часов без доступов и проверки реальной БД ненадёжна. Это несколько самостоятельных исправлений и интеграционных проверок, а не один оставшийся шаг публикации. P1-расширения (почтовая доставка, отдельная генерация PDF, видео) можно отложить.

## Что не проверено

Публичный deploy и его конфигурация, реальные RLS-запросы anon, транзакции/конкурентность реального Supabase, чистая установка, полная история на наличие секретов, dependency security audit, реальная экранная клавиатура iOS/Android, Lighthouse, печатный PDF, полный accessibility аудит, визуалы рекламы, обе UTM-ветки end-to-end, полный provenance всех финансовых и правовых утверждений.

Код приложения в этом аудите не исправлялся. Создан настоящий отчёт проверки; прежний QA-report сохранён для сопоставления, его отметки не следует считать достаточными доказательствами.
