## Подтверждение целого пути аналитики

Сессия `3a8ef836-243f-4487-962d-641b8e682c0d`, UTM `ad_b`, содержала:

- `landing_observed`;
- `comparison_viewed`;
- `calculator_used` с IVV;
- `lead_cta_clicked` с `ctaLocation=calculator`;
- `form_started`;
- `form_submit_attempted`;
- `report_opened` с IVV.

Все события и submission относятся к одной сессии. Порядок server timestamps частично отличается от смыслового порядка действий из-за асинхронной доставки; скрипт считает distinct sessions, а не последовательность временных меток. Измерение полного нового expiry/recovery через 30 минут и всех возможных interleavings этим коротким тестом не доказывается.

В production оставлены две синтетические заявки проверки: `audit-4465301@example.com` (UI) и `audit-concurrency-4465301@example.com` (параллельные POST). Для каждого проверенного requestId подтверждена одна submission. Они и сессия аудита не являются реальными рекламными конверсиями.

## Что ещё осталось

### 1. Согласовать поведение изменённого requestId с планом и QA

При повторе `a95b1299-530d-4584-90ed-b0885cf3859c` с другим email и суммой production вернул 200, `isDuplicateRequest:true`, исходные SPY/250000. Данные не перезаписались — это полезное свойство. Но §10.2 плана требует безопасно отклонять изменённое содержимое одной попытки; `docs/qa-report.md` T18 прямо утверждает, что сервер его отклоняет.

RPC не сравнивает нормализованный email/содержимое с исходной submission, а тест T18 (`tests/backend.test.ts`) ожидает именно `success:true`. Нужно либо реализовать сравнение канонического payload/hash с отказом при конфликте, либо явно пересмотреть решение и документацию. До этого нельзя отмечать этот пункт как пройденный по первоначальному критерию.

Риски конкурентности функции проверены ограниченно: два live запроса прошли без дублей, но схема check → insert в RPC всё ещё допускает конфликт уникальности при ином перекрытии запросов. Нужна устойчивая обработка конфликта requestId в самой функции, если требуется гарантия для любого одновременного повтора. В этом аудите такой отказ не воспроизведён и не объявляется подтверждённым live дефектом.

### 2. Довести проверяемость документации

- `docs/handoff.md` утверждает наличие определённого MDE, но `docs/experiments.md` по-прежнему содержит 1000 sessions, alpha/power без величины эффекта, обосновывающей sample size.
- `README.md` оставляет внутренние `file:///c:/...` ссылки. На GitHub нужны относительные пути.
- AI-log теперь честно объясняет наличие summary вместо raw export. Это улучшение, но требуемого заданиями экспортированного разговора в репозитории всё ещё нет. Нужен пригодный для передачи экспорт с удалёнными секретами/PII либо явное ограничение в письме; нельзя называть summary исходным экспортом.
- T07 теперь действительно требует исключение, но моделирует повреждённый вход, а не отказ реального storage; T14 и T20 улучшены до вызова handler, T15 остаётся проверкой текста миграции. Матрица должна различать unit, handler и live evidence.
- `report:funnel` теперь сообщает ошибку чтения, но `run().catch(console.error)` не выставляет ненулевой exit code. Для автоматизации это всё ещё неуспешный контракт ошибки, хотя ложные нули устранены.

### 3. Закончить источники и финальный QA

- Неподтверждённые числа о 1-cent spread и диапазоне FX-комиссий убраны; это закрывает существенную часть замечаний к copy.
- Налоговые ставки/условия и некоторые обобщения о US ETF/KID/крупнейших фондах ещё не имеют требуемой трассировки каждого утверждения к первичным доказательствам в dataset. В этом аудите выполнялась проверка наличия источников, не юридическая/налоговая экспертиза.
- Финансовые значения Hero/report всё ещё частично продублированы в JSX; обновление dataset может разойтись с текстами.
- Lighthouse mobile и визуальная проверка нового PDF остаются неподтверждёнными в этом аудите. Прежняя проверка PDF пользователем относилась к более раннему содержимому.
- Privacy всё ещё обещает автоматическое удаление через 30 дней; расписание запуска cleanup в репозитории не найдено, внешний scheduler не проверен. Нужно обеспечить процесс или уточнить описание.

Остальные ограничения — общее усиление, а не причины отрицать уже проверенную работоспособность MVP: строгие enum свойств каждого analytics event, обработка provider errors в создании/отзыве sessions, пагинация большого funnel, полный аудит Git history/секретов и зависимостей. Точная сумма удалена из штатного report event, но schema всё ещё разрешает поле `amount`.
